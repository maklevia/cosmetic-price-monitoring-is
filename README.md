# Cosmetics Price Monitoring IS

Information system for tracking cosmetic product prices across online stores, with
user collections, price-drop notifications, authentication, and an observability
stack planned for the university project.

## Local development

### Requirements

- Node.js 22+
- npm
- PostgreSQL 15+
- Docker Desktop with Compose (optional, for the full containerized stack)

Docker Compose can run the web app, backend, workers, and optional Telegram bot
together; see [Docker stack](#docker-stack).

### 1. Install dependencies

```bash
npm ci
```

### 2. Configure environment

```bash
cp .env.example .env
```

Fill in the database credentials and JWT secrets. `.env` is gitignored.

### 3. Start PostgreSQL

Use a local PostgreSQL installation, or run a one-off container if you have Docker:

```bash
docker run -d \
  --name cosmetics-price-monitoring-db \
  -e POSTGRES_USER=cosmetics \
  -e POSTGRES_PASSWORD=cosmetics \
  -e POSTGRES_DB=cosmetics_price_monitoring \
  -p 5432:5432 \
  -v cosmetics_price_monitoring_pgdata:/var/lib/postgresql/data \
  postgres:15-alpine
```

The auth service uses a separate database and role on the same PostgreSQL server:

```bash
docker exec cosmetics-price-monitoring-db psql -U cosmetics -d postgres \
  -c "CREATE ROLE auth_service LOGIN PASSWORD 'auth_service';"

docker exec cosmetics-price-monitoring-db psql -U cosmetics -d postgres \
  -c "CREATE DATABASE cosmetics_auth OWNER auth_service;"
```

These commands only need to be run once. If the role or database already exists,
skip them.

### 4. Run migrations

```bash
npm run migrate
npm run migrate:auth
```

### 5. Start the services

In separate terminals:

```bash
npm run dev:api
npm run dev:auth
npm run dev:frontend
npm run dev:bot
```

The auth service owns credentials and refresh tokens in `cosmetics_auth`.
The main API only validates access JWTs and stores user profiles in
`cosmetics_price_monitoring`. User IDs are generated by the auth database and
stored explicitly in the main `Users` table; the existing foreign keys from
collections and notifications still point to `Users.id`.

Existing users from the old in-API auth module must be recreated or migrated
into the auth database. A fresh local database starts with no users.

The API no longer schedules cron jobs. Start the background services separately:

```bash
npm run dev:scheduler   # cron schedules only; enqueues jobs
npm run dev:parser      # consumes parse/discovery jobs
npm run dev:notifier    # consumes notification dispatch jobs
```

- Frontend: http://localhost:5173
- API: http://localhost:3001
- Auth service: http://localhost:3002
- The Telegram bot requires a real `TELEGRAM_BOT_TOKEN` in `.env`.
- `ACCESS_TOKEN_SECRET` and `REFRESH_TOKEN_SECRET` must be the same for the
  API and the auth service.
- Parser workers can be scoped to one store with `PARSER_STORE=eva`,
  `PARSER_STORE=makeup` or `PARSER_STORE=notino`. Without it, one worker
  processes all stores.
- Use `PARSER_CONCURRENCY`, `PARSER_DELAY_MS`, `PARSER_POLL_MS` and
  `NOTIFIER_POLL_MS` to tune the workers.

### Build

```bash
npm run build
```

## Docker stack

The Compose stack contains:

- `postgres` — main and auth databases on one PostgreSQL server;
- `migrate` — one-shot service that runs both TypeORM migration sets;
- `api` — main HTTP API, internal port `3001`;
- `auth-service` — auth HTTP service, internal port `3002`;
- `web` — nginx serving the built frontend and proxying `/api` and `/auth`;
- `scheduler` — one cron/scheduler process;
- `parser-worker` — consumes parse and discovery jobs;
- `notifier` — consumes notification-dispatch jobs;
- `bot` — optional Telegram bot, enabled with the `bot` Compose profile.

The browser uses the web container at http://localhost:8080. Only this port is
published, and it is bound to `127.0.0.1`. API, auth, and PostgreSQL are
reachable only inside the Docker network.

### 1. Configure Docker environment

```bash
cp .env.docker.example .env.docker
```

Set real secrets in `.env.docker`. The file is gitignored.

Inside Compose, services use `DB_HOST=postgres` and `AUTH_DB_HOST=postgres`;
containers reach PostgreSQL on its internal port `5432`. PostgreSQL is not
published on the host.

`NODE_ENV=development` is intentional for local HTTP. With
`NODE_ENV=production`, auth cookies become `Secure` and browsers will not send
them over plain HTTP. Switch to production mode together with HTTPS.

`FE_ORIGIN` may contain a comma-separated list. The Docker stack allows the
nginx web origin (`http://localhost:8080`). Local `.env` keeps the Vite origin
(`http://localhost:5173`) for `npm run dev:frontend`.

### 2. Build and start

```bash
docker compose --env-file .env.docker config
docker compose --env-file .env.docker up -d --build
```

`migrate` must finish successfully before `api` starts. `auth-service` waits for
the API because signup calls the internal user-profile endpoint.

Check the result:

```bash
docker compose --env-file .env.docker ps
docker compose --env-file .env.docker logs -f api auth-service
```

`migrate` is expected to show `Exited (0)`; it is a one-shot container, not a
long-running service.

Open the application at http://localhost:8080. The web container serves the
SPA and proxies:

- `/api/*` to the API;
- `/auth/*` to the auth service;
- `/api/internal/*` is blocked at nginx.

API and auth are not published on the host. To inspect them, run commands
inside the Compose network:

```bash
docker compose --env-file .env.docker exec web wget -qO- http://api:3001/
docker compose --env-file .env.docker exec web wget -qO- http://auth-service:3002/
```

### 3. Start only the core stack first

```bash
docker compose --env-file .env.docker up -d postgres migrate api auth-service web
```

Then start the background processes:

```bash
docker compose --env-file .env.docker up -d scheduler parser-worker notifier
```

Run exactly one `scheduler`. Multiple schedulers can enqueue duplicate jobs.
The parser queue uses `FOR UPDATE SKIP LOCKED`; verify parser behavior before
scaling that service.

### 4. Start the Telegram bot

The bot is behind the `bot` profile because it needs a real Telegram token.
Set `TELEGRAM_BOT_TOKEN` in `.env.docker`, then start it with:

```bash
docker compose --env-file .env.docker --profile bot up -d bot
```

Without the profile, the normal backend stack does not start the bot.

### 5. Stop

```bash
docker compose --env-file .env.docker down
```

This keeps the PostgreSQL volume. To delete the database and rerun the init
script from scratch:

```bash
docker compose --env-file .env.docker down -v
```

The auth database and role are created by
`docker/postgres/init/01-auth-database.sh` only when the volume is initialized
for the first time.

PostgreSQL is not published on the host. To inspect it:

```bash
docker compose --env-file .env.docker exec postgres psql \
  -U cosmetics -d cosmetics_price_monitoring
```

## Repository layout

```text
api/
  src/entrypoints/   api, scheduler, parser and notifier process entrypoints
  src/jobs/          scheduling and job-processing logic
  src/modules/job/   job entity, queue interface and PostgreSQL queue
  src/modules/       domain modules (product, notification, user, channel, internal)
auth-service/
  src/modules/auth/  signup, login, refresh-token rotation, logout, password reset
  src/entities/      credentials and refresh tokens
frontend/            React + Vite + Chakra UI
telegram-bot/        Telegraf bot
docker/              backend/web images, nginx config, PostgreSQL init scripts
docker-compose.yml   full container stack
```
